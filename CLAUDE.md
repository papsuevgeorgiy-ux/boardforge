# BoardForge — генератор узоров для торцевых разделочных досок

Инструмент, по результату которого столяр реально изготавливает доску: узор,
раскрой, расчёт материалов, пошаговая инструкция, PDF.

## Главный инвариант

**Доска — это программа, а не картинка.** Проект хранится как последовательность
столярных операций (`Glue` → `Crosscut` → `StandOnEnd` → `Assemble` → ...).
Узор, карта раскроя, расход материала и инструкция **выводятся** из программы.

Из этого следуют жёсткие правила:

- Никогда не храни узор как готовый растр или как «истину». Узор — производная.
- Любая новая фича сначала отвечает на вопрос: «какую операцию она добавляет
  или какую характеристику из программы вычисляет?»
- Если что-то нельзя выразить программой операций — это нельзя изготовить,
  и в приложении этого быть не должно.

## Геометрия

Ячейки узора — **произвольные полигоны**, не клетки сетки. Угловые резы
(ёлочка, шеврон, кубы) дают параллелограммы. Работаем через `shapely`:
рез = пересечение с полосой, пересборка = аффинные преобразования.

Никаких двумерных массивов цветов в ядре.

## Единицы измерения

- Внутри ядра **всегда миллиметры**, `float`.
- Дюймы и доли дюйма — только на границе ввода/вывода (форматтеры).
- Углы — градусы во всём домене; перевод в радианы локальный, на месте
  вычисления.

## Все размеры в программе — чистовые

Пропил, строгание и обрезка кромок **не входят в геометрию**. Программа
оперирует готовыми размерами детали; припуски вычисляются обратным ходом
слоем `calc/` и попадают только в раскрой, смету и список закупки.

Отсюда: смена диска на тонкий меняет расход материала, но не рисунок, а тест
на воспроизводимость геометрии не зависит от настроек станка.

## Технологические припуски — учитываем всегда

- Пропил (kerf) съедает материал при каждом резе.
- Строгание после каждой склейки съедает толщину с обеих сторон.
- Обрезка кромок по периметру после каждой склейки.

Расчёт материала без этих трёх пунктов считается багом. Место им — в `calc/`,
не в геометрии.

## Стек

- Ядро: чистый Python, `shapely` + `numpy`, **без зависимостей от UI**
- 2D-рендер: собственный SVG-writer (без библиотек), вектор идёт и на экран, и в PDF
- 3D: `trimesh` → экспорт `.glb` → `<model-viewer>` в браузере, JS не пишем
- Web UI: FastAPI + Jinja2 + HTMX, вся логика на Python
- PDF: WeasyPrint по тому же HTML
- CLI: `argparse` из стандартной библиотеки (Р17); `rich` — при необходимости на Дне 7
- Формат проекта: JSON программы + `schema_version`

## Команды

```bash
uv sync                    # установка
uv run pytest              # тесты
uv run pytest -x -q        # быстрый прогон при разработке
uv run ruff check --fix .  # линт
uv run ruff format .       # формат
uv run boardforge serve    # веб-интерфейс на localhost
uv run boardforge --help   # CLI
```

## Структура

```
src/boardforge/
  core/        # операции, геометрия, породы — без UI и без I/O
  render/      # SVG, 3D-меш
  calc/        # раскрой, материалы, отходы, себестоимость, предупреждения
  io/          # загрузка/сохранение проекта, PDF
  web/         # FastAPI + шаблоны
  cli/         # Typer
tests/         # зеркалит src/
docs/          # доменная модель, архитектура, план
```

## Правила работы с кодом

- Ядро (`core/`) не импортирует ничего из `web/`, `cli/`, `render/`.
- Каждая операция ядра покрывается тестом до того, как появится в UI.
- Тест на изготовимость: любой сгенерированный узор должен воспроизводиться
  из своей программы бит-в-бит.
- Комментарии только там, где неочевидно «почему». Не описывай, что делает код.
- Названия в коде — английские, строки интерфейса и docstring — русские.
- Не добавляй зависимость, не спросив.
- **Не ослабляй существующий тест, чтобы прошёл новый случай.** Порог, набор,
  диапазон в тесте — это зафиксированное ожидание, а не помеха. Либо исключи
  новый случай из набора, либо объясни, почему исходное ожидание было неверным,
  и дождись подтверждения. Красный тест — это сообщение, а не препятствие.

## Дополнительный контекст

Перед работой над ядром прочитай `docs/domain.md` — там столярная модель,
породы, припуски и определение DSL. Принятые решения по спорным местам домена —
`docs/decisions.md`, он имеет приоритет над `domain.md` при расхождениях.
Перед архитектурными решениями — `docs/architecture.md`. Текущий прогресс
и задачи — `docs/plan.md`, отмечай выполненное галочками по ходу.

Обзор проекта целиком — `docs/PROJECT.md`: что где лежит, ключевые модули,
известные проблемы, бэклог. Читай её, когда нужна общая картина или непонятно,
где что находится.
