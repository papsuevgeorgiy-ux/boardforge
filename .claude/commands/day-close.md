description: Закрыть день плана
argument-hint: N (номер дня)
---

Открой `docs/plan.md`, найди день $ARGUMENTS. Дальше иди строго по фазам,
между фазами останавливайся: не начинай следующую, пока не показал результат
предыдущей.

## Правила на всё время работы

- Каждое утверждение о состоянии проекта — с доказательством: файл, строка,
  вывод команды. Утверждение без доказательства произноси словом «предполагаю».
- Не пиши ничего в `docs/` и `CLAUDE.md`, пока не показал, что именно
  собираешься изменить, и не получил «да».
- Тесты не ослабляй. Если тест мешает — это находка для фазы 2, а не правка.
- Карта проекта лежит в репозитории — `docs/PROJECT.md`. Правь её там же
  и по тому же правилу: сначала покажи, потом применяй.

## Фаза 0 — рабочее дерево

```powershell
git status --short
git log --oneline -1
```

Покажи: есть ли незакоммиченное, на чём стоит HEAD. Затем спроси у меня,
прогонялся ли `/check` на этом HEAD. Если не прогонялся или дерево грязное —
вызови `/check` здесь. Дальше не иди, пока он не зелёный.

## Фаза 1 — сверка карты с кодом

Прочитай `docs/PROJECT.md`. По каждому её утверждению — статус:

- **подтверждается** — файл и строка;
- **противоречит** — что в карте, что в коде, доказательство;
- **в коде нет** — утверждение висит без опоры.

Отдельным списком: что появилось в репозитории и в карте не упомянуто —
новые модули, команды CLI, выходные файлы в `out/`, разделы `docs/`.
Сравни дерево карты с фактическим (`git ls-files`), число тестов — с выводом pytest.

Результат фазы — отчёт. Ни одной правки файлов.

## Фаза 2 — то, чего в коде нет

Этого не выводи из репозитория и не сочиняй. Спроси у меня:

- какие пункты Known issues день закрыл, какие изменил, какие появились;
- что уходит из бэклога и что в него добавляется;
- какие решения дня требуют номера в `docs/decisions.md` и **почему** решение
  именно такое — константа в коде не помнит своего обоснования;
- что сделано намеренно не сделано (это тоже строка бэклога, а не пробел).

Задай вопросы списком и жди ответа.

## Фаза 3 — запись

По ответам фазы 2 подготовь правки, покажи их до применения:

- `docs/decisions.md` — новые Р-номера, каждое решение с обоснованием и с ценой
  альтернативы, которую отвергли;
- `docs/domain.md` — если менялось понимание столярного процесса, а не кода;
- `docs/plan.md` — галочки дня $ARGUMENTS и запись в раздел «Журнал»:
  что сделано, что нашлось по дороге, что перенесено;
- `CLAUDE.md` — только если появилось правило, которое иначе нарушится снова;
  держи файл под 200 строк, лишнее уводи в `docs/`;
- `docs/PROJECT.md` — сводка правок из фазы 1 плюс ответы фазы 2.

Разбор бага, найденного по дороге, не оставляй только в комментарии рядом с кодом:
через два дня его там никто не откроет. Место — Known issues или `decisions.md`.

## Фаза 4 — проверка глазами

Тесты не видят часть дефектов. Собери выходы и назови мне, что смотреть:

```powershell
uv run boardforge swatches
uv run boardforge examples --scale 5
uv run boardforge contact-sheet
start chrome "$PWD\out\contact-sheet.svg"
```

Плюс выходы, появившиеся в этот день. Для каждого сформулируй конкретный вопрос
(«читаются ли буквы пород на чёрно-белой распечатке», «совпадает ли раскрой
на листе с числами сметы»), а не «посмотри, всё ли хорошо». Жди моего ответа —
сам зелёным этот пункт не помечай.

## Фаза 5 — фиксация

Только после «да» на фазе 4. Сначала посмотри, менялся ли с фазы 0 код:

```powershell
git status --porcelain -- . ':!*.md'
```

Вывод читай только как пусто/непусто: разбирать его как список путей не нужно,
у `--porcelain` в начале строки стоят префиксы статуса.

Пусто — фазы 1–4 тронули только документы, проверка фазы 0 в силе, иди сразу
к git-части. Непусто — сначала `/check`, и только потом:

```powershell
git add -A
git commit -m "День $ARGUMENTS: <что закрыто>"
git tag day$ARGUMENTS
git push origin main --tags
```

В конце — три строки: что день дал, что осталось незакрытым, что из этого
блокирует следующий день. Пункт с блокировкой назови отдельно, даже если он
выглядит мелочью: день начинается с него, а не с плана.
