# Архитектура

## Слои

```
core/    операции, геометрия, породы, валидатор,    ← без I/O, без UI
         обратная задача по габаритам
  ↓
calc/    раскрой, материалы, отходы, себестоимость
  ↓
render/  SVG (2D), trimesh → .glb (3D)
  ↓
io/      проект (JSON), PDF (WeasyPrint)
  ↓
web/ cli/  оболочки
```

Зависимости только сверху вниз. `core/` не знает о существовании остальных.

## Ключевые решения и их причины

**Геометрия на `shapely`, а не на сетке.**
Угловые резы дают параллелограммы и обрезки. Одно универсальное представление
(полигон + порода) закрывает и шахматку, и кубы, и ёлочку. Цена — производительность,
лечится кэшированием.

**Кэш по хешу программы.**
Результат каждой операции кэшируется по хешу префикса программы. Правка последней
операции не пересчитывает всё. Ключ — стабильная сериализация операций.

**Собственный SVG-writer.**
Один вектор идёт в браузер, в PDF и на печать 1:1. Никаких растровых
рассинхронов между экраном и цехом.

**Рендер в два слоя.**
Текстура стоит втрое дороже всего остального: на доске 30×20 структура рисуется
за 78 мс, текстура — за 286 мс. Живое редактирование не может ждать второе,
поэтому рендер разнесён:

| Слой | Что рисует | 600 ячеек |
|---|---|---|
| Структура | полигоны, клеевые швы, кромка | 78 мс, 60 КБ |
| Текстура | кольца, лучи, обрезка по ячейке | 286 мс, 749 КБ |

Контракт между ними жёсткий: структура со вставленной текстурой — **побайтово**
полный документ. Иначе превью в браузере разошлось бы с тем, что уходит в файл
и в печать. В структуре остаётся пустая группа `texture`, и слой встаёт в неё.

В UI структура приходит сразу, текстуру браузер запрашивает сам через 200 мс
после того, как структура встала. Частые правки этот отсчёт сбрасывают, так что
текстура догоняет, когда крутить перестали.

**3D без JS.**
`trimesh` собирает меш из полигонов ядра с фаской и экспортирует `.glb`.
Браузер показывает через `<model-viewer>`. Мы не пишем и не отлаживаем three.js.

Фаска сделана резом ячейки по линии фаски, без булевых операций и без второй
библиотеки: подробности и цена ошибки — в Р29. Триангуляцию крышки даёт
`shapely.constrained_delaunay_triangles` — ячейка после обрезки бывает
невыпуклой, и веер из первой вершины на ней разваливается.

Просмотрщик и модель грузятся **по кнопке**, а не со страницей: вместе они
около мегабайта, а редактор должен подниматься быстро. Тот же приём, что
и с текстурой, только повод другой — там задержка, здесь размер.

**PDF тем же вектором.**
WeasyPrint печатает ровно ту разметку, которая ушла в `.html`, не пересобирая
её второй раз. Импорт `weasyprint` живёт внутри функции: без системного GTK
он падает `OSError` и наверху модуля утянул бы за собой весь пакет, включая
`serve` и `swatches`, которым принтер не нужен.

**Инструкция — производная, как и всё остальное.**
Шаг — операция программы, картинка шага — состояние верстака после неё.
Состояния берёт `Program.trace()` из того же прохода, что и `run()`; исполнять
префиксы `operations[:k]` нельзя — большинство из них валидатор законно
не пропускает (Р28).

**История правок — программы целиком.**
Обратной операции к «подобрать габарит» не существует: подбор переписывает
сразу несколько операций и меряет результат исполнением. Поэтому undo хранит
прежнюю программу, а не описание правки, и все правки идут через единственную
дверь `Editor.set_program`.

**HTMX вместо SPA.**
Весь интерфейс — Python + шаблоны. Обмен — фрагменты HTML. Локально round-trip
незаметен. Перерисовывать надо частично: отдельные фрагменты, не всю страницу.

**Габариты — производная, обратная задача переписывает программу.**
`core/fitting.py` не хранит целевой размер: он правит параметры операций и
**меряет** попадание исполнением программы, а не второй формулой. Формула
не знает про обрезку, сдвиги рядов и остаток от торцовки — показывать по ней
размер значит показывать не то, что человек получит. Оси и рычаги — в
`domain.md`, раздел 2.1.

**Проект — программа, а не снимок.**
JSON со списком операций и `schema_version`. Читаемый, диффабельный,
воспроизводимый. Миграции схемы — отдельный модуль с версии 2.

## Чертежи для мастерской

Отдельный режим рендера: чёрно-белый, каждая деталь подписана буквой породы,
проставлены размеры и номера шагов. Печатается на офисном лазернике.
Цветной рендер — для превью, ч/б — для работы.

## Производительность

- Живое редактирование должно укладываться в ~100 мс на перерисовку — это про
  **структуру**; текстура в этот бюджет не влезает и в него не ставится.
- Тяжёлые вещи (оптимизация раскроя, эволюционные генераторы) — в отдельном
  потоке/процессе, с прогрессом в UI.
- Бенчмарк в тестах: доска 20×30 ячеек, 3 склейки — фиксируем верхнюю границу.

## Оптимизация раскроя

Одномерная задача раскроя (реек из досок стандартной длины):
first-fit-decreasing как база + локальный поиск с ограничением по времени.
Не гонимся за оптимумом, гонимся за предсказуемостью и объяснимостью:
пользователь должен видеть, почему нужно именно столько материала.

## Генераторы узоров

Работают **над пространством программ**, а не над пикселями. Мутируют состав
щита, углы резов, сдвиги и отражения. Любой результат изготовим по построению.
Фитнес-функция для эволюционного режима: контраст, ритм, симметрия,
экономичность, реализуемость.
